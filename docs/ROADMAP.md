# 路线图

主线只有一条：

```
双人 P2P → 四人 P2P → 游戏捕获 → 分屏 → 动态画质 → Overlay → TURN → 稳定性 → EXE
```

**做到 Overlay 之后这个软件就已具备实际使用价值。** 后面的 TURN、重连和性能优化
是把「能玩」变成「稳定地玩」。

> **版本定位（2026-09-18 拍板）：v1.0 以「朋友间内部使用合格」收口。**
> M0~M6 全 ✅ —— 正是上面那句「Overlay 之后即有实际使用价值」。
> P2P 打洞的连接法不适合公开服务（信令无鉴权）；将来若要做公开服务，
> 另起网络方案（鉴权 / TURN / 可能换架构）再谈。M7~M10 暂不做（理由见各段标注）。
> 本仓库现按开源维护：欢迎 issue / fork / PR，M7~M10 是最合适的参与切入点。

每个里程碑都必须先跑通验收再进入下一个，不要并行推进。

## ✅ M1 双人 P2P

**目标**：两台不同电脑互相看到屏幕。**第一个关键里程碑。**

**交付**

- `MeshManager` + `PeerLink`：每人一个 `RTCPeerConnection`，offer/answer/ICE 全流程
  （原规划的 `PeerManager` 按「成员同步」与「单链路状态机」拆成两个，理由见
  `docs/ARCHITECTURE.md` 第 5 节）
- 每条链路的主动方由 `selfPeerId > remotePeerId` 决定，只有主动方创建 video m-line
  并发起首次协商；完整协商仍走 Perfect Negotiation（polite / impolite / ignoreOffer）
- 远端视频渲染、连接状态机（new / connecting / connected / disconnected / failed / closed）
- 未建链路时先到的信令会被缓冲，链路建立后重放（避免双方互等造成死锁）
- 合成源（canvas 动画）：让「链路是否通」与「捕获权限是否拿到」分开验证
- 按观看者独立控画质的通道已打通（`quality-request` → `setParameters`），M5 直接接上

**验收**

- [x] 双向看到对方画面
- [x] 断开一端，另一端连接正确清理并显示状态

```
npm run smoke:p2p                 # 2 人 + 断开场景
npm run smoke:p2p -- --peers 2,4  # 再加一轮 4 人
npm run smoke:all                 # 连 M0 信令验收一起跑
```

**验收方式说明**

本地不具备两台实体电脑跨 NAT 测试的条件，M1 的验收由本机自动化承担：
拉起 2~4 个**真实 Electron 渲染进程**跑完整协商，结论取自
`getStats()` 的 `framesDecoded` / `bytesReceived` / `frameWidth`，不靠肉眼看。

- **自动化能证明**：双向协商本身是通的 —— 真实 SDP 交换、真实编解码、真实解码帧数持续增长。
- **自动化不能证明**：跨 NAT 打洞。本机全部连接落在 host candidate 上（`P2P/host`）——
  同一台机器上的两个客户端本来就该直连，这测不到任何 NAT 行为。
- **跨 NAT 已另行人工补验，见下一节。**

### ✅ 跨 NAT 实测（2026-09-17，人工）

**结果：异地电脑（另一个宽带、不同家）成功看到本机共享的画面。**

当前没有 TURN，ICE 候选只可能是 host 或 srflx，所以逐条排除即可：

| 候选类型 | 判定 | 理由 |
| --- | --- | --- |
| `relay` | 排除 | 未部署 TURN，ICE 根本不会产生 relay 候选 |
| `host` | 排除 | 私网地址跨公网不可路由 |
| ⇒ `srflx` | **剩下唯一可能** | 即打洞成功 |

> **证据边界（别过度声明）**：当时没记录画面瓦片底部的路径标签，上表是**逻辑推断**，
> 不是直接读数。要把它写成「已实测 `srflx`」，必须先补一次带标签的复测
> （判定方法见本节末与 `docs/REMOTE-TESTING.md` 第 3 步）。
> 另外这里只覆盖了**共享方向**（对端看到本机画面），反向未单独确认。

> **关于 `code=701` 的一次误判（2026-09-16 更正）**
>
> 早期版本把日志里的 `ICE 候选错误 ... code=701` 记成了「STUN 在当前网络下不可达」，
> 并据此推断 srflx 路径无法覆盖。**这个结论是错的。**
>
> 701 的原文是 `STUN host lookup received error` —— 属于 **DNS 解析**失败，
> 而且它只让**部分**节点失败，不影响同一 ICE 配置里其他节点成功。
> 用 `npm run check:stun` 在 Chromium（真正跑视频的运行时）里逐个验证：
> 本机能拿到 srflx 候选（公网映射 `120.230.99.56`），NAT 类型为**锥形**。
>
> 真正的问题是默认 STUN 列表里混了一个无效节点（`stun.qq.com`），
> 既贡献 701 噪音又拖慢 ICE 收集，已移除。
>
> 判断 STUN 是否可用**不能看有没有报错，只能看有没有 srflx 候选**。
> 完整方法和实测数据见 `docs/REMOTE-TESTING.md`。
- **断开场景**：主进程真实销毁一个窗口（等价于客户端崩掉），
  其余客户端约 **0.2 秒**完成清理（链路、远端流、成员列表、`RTCPeerConnection` 已 close）。

**顺带验证到的**（不构成里程碑完成，仅供后续参考）

- 4 人 Mesh 能建起 12 条有向链路且双向都有画面 —— M3 的一部分，但 M3 的
  「中途退出后再加入、链路正确重建」尚未验证。
- 按观看者独立控画质：同一个人对 4 个观看者分别持有独立 sender，
  被请求的那一路单独升到 4 Mbps/1080p 档，其余保持 1.5 Mbps/540p 档。

**2026-09-17 顺带修掉的一个缺陷**

`ShareSession.stopShare()` 原先只在 `reason === 'user'` 时通知对端，于是有两种情况会让
**对端永远停在一个收不到画面的「共享中」**（且在对端离开房间前不会自愈）：

- 用户关掉被共享的窗口 → 本地已停共享，但对端不知道
- 换源失败 → 旧源已停、新源没起来，且没有任何路径能补发 `setSharing(false)`

改法：除换源外一律通知对端；换源路径改为**静默停旧源**（避免面板闪一帧「未共享」），
失败时由 `startShare` 自己补发 false 并把状态收回「未共享」。

**已知限制（必须对使用者说明，写进 README）**
