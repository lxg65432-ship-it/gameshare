# 架构说明

本文档记录 GameShare V0.1 的架构决策，重点是**动手前必须知道的技术约束**。
第 4 节列出的约束如果被忽略，轻则返工，重则直接导致验收标准无法达成。

---

## 1. 顶层设计

```
        ┌──────────────── 信令服务器（Node + Socket.IO） ────────────────┐
        │  房间管理 · 成员状态 · 信令转发                                │
        │  不碰视频：不转码、不录制、不落盘                              │
        └──────────────────────────┬────────────────────────────────────┘
                                   │  WebSocket（仅信令 + ICE）
          ┌──────────────┬─────────┴────────┬──────────────┐
          │              │                  │              │
       玩家A ────────── 玩家B ──────────── 玩家C ───────── 玩家D
          │   ╲            ╱   ╲              ╱   │
          └──── WebRTC P2P Mesh（最多 6 条链路）─────┘
                视频直连；打不通才降级 TURN 中继
```

四人满员时共 6 条 P2P 链路。每个客户端对每个远端成员持有一个独立的
`RTCPeerConnection`，这是能做到「针对不同观看者给不同画质」的前提。

**服务器职责边界**：只做房间管理、成员状态、信令与 ICE 交换。第一版不引入
数据库、不引入 SFU、不做转码。服务端重启后房间全部丢失，这是 V0.1 明确的取舍。

## 2. 信令流程

### 建房 / 进房走 ack，状态广播走事件

`create-room` / `join-room` / `leave-room` 使用 Socket.IO 的 ack 回调返回明确成败，
而不是「客户端发事件 + 等服务端广播结果」。这类请求有唯一确定的结果，走 ack
可以让客户端拿到线性可读的代码，不必维护 requestId 关联表。

`peer-joined` / `peer-left` / `peer-updated` 以及全部 P2P 信令走事件广播。

### 谁发起 offer

原规划是「后加入者向已存在的每个成员逐个发起 offer」。实现时改成了更稳的等价方案：

**每条链路的主动方由 `selfPeerId > remotePeerId` 决定，只有主动方创建 m-line 并发起首次协商。**
用随机 peerId 比大小等价于抛硬币，但两端算出的结果必然相反，正是这里需要的性质。

改这一下的原因：原方案在「两人几乎同时加入」时没有确定答案 ——
双方都认为自己是后加入者，同时 offer 就变成 glare。
按 peerId 比大小天然把这个平局判掉，同时保留了「每条链路只有一个发起方」这个关键性质。
完整协商仍然按 Perfect Negotiation 实现（polite / impolite、`ignoreOffer`），
因此后续任何一方都可以重新协商。

详见 4.7。

### `fromPeerId` 只采信服务端注入的值

客户端发送定向信令时只填 `targetPeerId`，不填 `fromPeerId`；
服务端转发前把真实的 `socket.id` 注入信封。接收端只读信封里的 `fromPeerId`。
验收脚本里有一条专门伪造 `fromPeerId` 的用例，用于守住这个边界。

## 3. 数据流

```
采集源（窗口 / 屏幕）
   │  desktopCapturer → getDisplayMedia（video，Windows 上附 audio:'loopback'）
   ▼
MediaStreamTrack（源分辨率，如 1920×1080）+ 系统声音轨（整机混音）
   │
   ├─► RTCPeerConnection(B) ─► RTCRtpSender(video) ─► setParameters(画质档位)
   │                        └► RTCRtpSender(audio) ─► 固定 opus，无档位
   ├─► RTCPeerConnection(C) ─► 同上
   └─► RTCPeerConnection(D) ─► 同上
                                                     ▲
                          quality-request（来自观看者）
```

每个观看者一条独立链路、一次独立编码。**同一条 `MediaStreamTrack` 被多个
`RTCRtpSender` 复用是允许的**，浏览器内部会为每个 sender 独立编码。

每条链路上有两条 m-line：video 和 audio。画质档位只作用于 video 的 sender
（音频没有档位可言）。观看者对每路的静音是**纯本地**的，不进这条数据流。

## 4. 硬约束

### 4.1 独占全屏游戏无法被 Overlay 覆盖

规格文档写的是「一边全屏玩游戏，一边看好友小窗」。这条对**独占全屏
（Exclusive Fullscreen）无效**：独占全屏由 DWM 让权给游戏，任何
`setAlwaysOnTop(true)` 的窗口都会被盖住，`screen-saver` / `pop-up-menu`
各层级都试过也一样。

**可行路径**：无边框窗口化 / 窗口化全屏（Borderless Windowed）。
M6 的验收标准应写成「在无边框窗口化模式下 Overlay 保持可见且可交互」。

**判定一个游戏属于哪种「全屏」，办法是看它能不能被采集到**：
2026-09-17 实测以撒（Binding of Isaac）在全屏状态下**能正常抓到画面**，
说明它走的是无边框全屏、DWM 仍在合成 —— 这种情况置顶窗口也能显示在它上面；
只有真独占全屏才会既黑屏、又让任何置顶窗口都盖不上去。
所以「这游戏能不能边玩边看好友画面」不需要用户去查设置，实测一次即可。

**浮窗置顶的实现**在 `apps/desktop/electron/window-mode.ts`：`setAlwaysOnTop(true)`
（层级写 `'screen-saver'`，Windows 上落到 `HWND_TOPMOST`），开关放在顶栏，
另注册一个**全局**快捷键 `Ctrl+Alt+G`。

快捷键必须是全局的：全屏游戏里鼠标在游戏里，点不到我们的界面；窗口级快捷键
（`webContents` 的 `before-input-event`）在窗口不聚焦时也收不到按键，
只有 `globalShortcut` 是进程外、全局生效的。**代价是多开客户端时只有一个窗口
能注册成功**（系统只允许一个进程占这个键），抢不到的那个在界面上标
「快捷键冲突」并说明「点开关作用一样」—— 不标出来的话，用户按了没反应
只会以为是软件坏了。

> **已验（`npm run check:topmost`，2026-09-17）**：开一个无边框全屏窗口模拟「游戏」，
> 截屏读像素判定谁在上层，三段对照全绿（不置顶 → 被盖住 / 置顶 → 盖住 / 游戏抢最前 → 仍盖住）。
>
> 剩下的边界是**独占全屏**：盖不住，也**改不了**（理由见 4.13）。
> **2026-09-17 需求方拍板不做** —— 突破它只能注入游戏进程，是另一个量级的工程且撞反作弊。
> 玩法改推荐「**无边框窗口化**」，实机跑下来这个模式挺好，就当它是验收口径。

### 4.2 上行带宽与编码次数是四人场景的物理瓶颈

发射端每多一个观看者就多一次完整编码。四人满员时，每个客户端要同时编 3 路。

| 场景 | 单客户端上行 | 单客户端并行编码数 |
| --- | --- | --- |
| 全部 GRID (540p30) | ≈ 4.5 Mbps | 3 |
| 1 人被聚焦 (FOCUS 1080p30) | ≈ 7 Mbps | 3 |
| 3 人同时被聚焦 (FOCUS_HIGH 1080p60) | ≈ 18 Mbps | 3 |

国内家宽上行普遍 20–50 Mbps，最坏场景能撑但没有余量，且需要显卡支持
3 路并行的硬件编码。

**结论**：M10 性能测试必须把「三人同时 FOCUS」列为最坏场景。
如果实测扛不住，退路是给 `FOCUS_HIGH` 加一个「同一时刻最多 N 路」的全局配额。

### 4.3 `scaleResolutionDownBy` 的基准是采集源，不是目标档位

`RTCRtpSender.setParameters()` 里的 `scaleResolutionDownBy` 只能缩小、不能放大，
且基准是**采集源实际编码分辨率**（`track.getSettings().height`）。

```ts
// 错误做法：把 2.0 写死
// 1080p 源 → GRID(540p) 确实是 2.0，但 1440p 源就变成 720p，档位全部错位

// 正确做法：运行时换算
const scale = computeScaleResolutionDownBy(track.getSettings().height, profile.targetHeight);
```

该函数在 `packages/protocol/src/quality.ts`，已处理「源小于目标时返回 1」的边界。

### 4.4 动态画质第一版用 `setParameters`，但要预留改用 simulcast 的位置

`setParameters` 是单编码 + 降尺度，切换档位会触发关键帧重建，肉眼可见
0.2～0.5 秒模糊。优点是实现快、能立刻验证链路。

若实测切换抖动明显，改用 simulcast（一次采集、多层编码由 WebRTC 调度）会平滑很多，
代价是上行带宽浪费（多层同时推）和编码器压力。

**因此 `QualityManager` 必须设计成可替换策略**：对外只暴露
`applyQuality(peerId, level)`，内部实现可以被整体替换。不要把
`setParameters` 的调用铺进 UI 层。

### 4.5 反作弊风险（README 明示，不进界面）

部分带反作弊（EAC / BattlEye / Vanguard 等）的游戏会把桌面捕获行为判定为
异常，存在封号风险；另有一批游戏直接阻止捕获，表现为黑屏或纯色帧。

**口径（2026-09-19 拍板）**：本软件的捕获走 WGC（Windows Graphics Capture），
系统级合成管线、不注入游戏进程 —— 主流反作弊不会因此封号；真正的限制是
「独占全屏抓不到，改无边框窗口化即可」。风险与限制统一写进 README
「已知限制」，**界面里不再放警示**：给小圈子用的开源工具，常驻警告只会
给使用者徒增心理负担，README 里查得到就够了。

### 4.6 原规划的 `packages/types` 已合并进 `packages/protocol`

两个包职责重叠且会互相引用，容易产生循环依赖与构建顺序问题。
类型定义全部收进 `protocol`，它是协议的唯一事实来源。
`packages/shared` 只放与协议无关的基础设施（日志、常量）。

### 4.7 每条 m-line 只能由一方创建（video 与 audio 同理）

**这是 M1 耗尽最多时间的一个坑，症状极具误导性：连接状态显示 `connected`、
信令日志一切正常，但画面只有一个方向有、或者两边互相看不见。**

原因：如果两侧都调用 `pc.addTransceiver('video', { direction: 'sendrecv' })`，
Chrome 会在 offer/answer 里生成**多条** video m-line；随后协商直接报
`The order of m-lines in answer doesn't match order in offer`。更麻烦的是，
Chrome 未必复用我们预先建好的那条 transceiver —— 它可能自己新建一条 `recvonly`，
于是我们在自己那条上写 `direction` 完全没有效果，`currentDirection` 永远是单向。

**落地的四条做法**（都在 `apps/desktop/src/rtc/PeerLink.ts`）：

1. `addTransceiver` 只由链路主动方调用一次，被动方一律只接受。
   主动方由 `selfPeerId > remotePeerId` 决定 —— 用随机 peerId 比大小等价于抛硬币，
   但两端结果一致，这正是此处需要的性质。
2. `direction` 恒定写 `sendrecv`，不随「是否正在共享」切换。
   开关共享只用 `sender.replaceTrack(track|null)` 表达，协商因此只发生一次。
3. **选 transceiver 要选「真正绑定了 m-line 的那条」，并且按媒体类型分别选**：
   `find(t => !t.stopped && t.mid !== null && t.receiver.track?.kind === kind)`，
   `kind` 取 `'video'` 或 `'audio'`。
   按 `transceiverCount === 1` 之类的前提去取，会在 Chrome 自行新增时取到死对象；
   只认 video 不认 audio，则视频通了、音频那条永远是单向（**有音轨、没有数据**，
   是最难从界面看出来的一类故障）。
4. 挂轨道必须串行在生成 offer 之前（`#pendingTrackApply`），
   否则会出现「m-line 建出来了但方向定成单向」。
   两条轨共用同一条串行队列 —— 挂载顺序就是 m-line 顺序。
5. **两条 m-line 的顺序必须两端一致：video 在前、audio 在后。**
   顺序就是我们 `addTransceiver` 的调用顺序。
   主动方在构造函数里按 video → audio 依次建；被动方一条都不建、只接受。
   顺序反了会直接报 `The order of m-lines in answer doesn't match order in offer`。

配套的兜底是 `#repairDirectionIfOneWay()`：仅主动方、最多重试 3 次，
在建连后 `[0, 1200, 3000]ms` 三个时点检查方向并纠正。

### 4.8 实际分辨率会低于档位标称值，验收要断言「实际 == 期望」

`scaleResolutionDownBy` 只是我们要求的下限，**Chrome 仍会在其上继续按带宽估计
自适应降分辨率**（`qualityLimitationReason=bandwidth`）。

M1 实测：720p 合成源、GRID 档（标称 960×540）实际编成 360×203；
FOCUS 档（scale=1.0）实际编成 480×270。相对关系却完全正确——
两条链路的编码尺寸之比正好等于 1.333，证明档位换算本身没问题，
被压掉的是绝对分辨率。

**因此验收断言必须写成「发送方实际落下去的 `scaleResolutionDownBy`
== 按源高度算出的期望值」，而不是笼统的「必须 > 1」**：
FOCUS 在 720p 源上按设计就等于 1（源低于目标档位时不放大），
写成 `> 1` 会把正确结果判成失败。`scripts/smoke-p2p.mjs` 里的
`expectedScaleResolutionDownBy` 就是为此存在。

验收脚本会把「解码分辨率」和「出分辨率」两列一起打印，
目的是区分「档位没生效」和「生效了但被带宽压下去」这两种完全不同的情况。

绝对分辨率偏低本身不一定是缺陷，但**对画面清晰度是实打实的损失**，
M5 / M10 需要在真实网络上确认默认档位是否够用；
必要时再考虑 `degradationPreference` 与 `contentHint` 的取值。

### 4.9 拆除链路的收尾回调必须按成员列表过滤

`MeshManager.removePeer()` 会调用 `PeerLink.close()`，而 `close()` 内部会
回调一次 `onStateChange('closed')`。这次回调**晚于** `ShareSession.#prunePeer()`：

```
peerLeft → 成员列表移除 → prunePeer 删掉 links[peerId] → syncMesh
         → removePeer → link.close() → onStateChange('closed')
         → 把刚删掉的 links[peerId] 又写了回来
```

结果是 state 里永远留着一个 `{ state: 'closed' }` 的幽灵条目：
UI 上多一个「已断开」的空格子，而且**再也不会消失** ——
对端已经不在成员列表里，不会再有事件来清理它。

这个 bug 是「断开一端」的自动化断言暴露出来的：成员列表、远端流、
`MeshManager` 链路映射都在 0.2 秒内清理干净了，唯独 `links` 里那条幽灵
一直挂到断言超时。

**规则**：链路归属由成员列表决定。`onStateChange` 里先判断该 peerId
是否还在房间里（`ShareSession.#isMember`），不在就丢弃。
这条规则同时把「`leaveRoom` 之后才到达的收尾回调」一并挡掉。

### 4.10 系统声音：采哪一路由策略层决定，静音只能按「人」

V0.1 原本不传声音，现已补上。三个必须先知道的事实：

> **2026-09-18 更正**：本节原先写着「callback 必须传 `audio: 'loopback'`」与
> 「Windows 没有按窗口分离音频的能力 —— 做不到只听这一个游戏的声音」。
> **两条都已不成立**，按现在的实现重写为下面第 1、2 条；第 3 条与静音那段仍然有效。
> 细节在 [4.15](#415-音频采集四种模式与-device-id2026-09-18)。

1. **只有 Windows 采得到系统声音**，但**采哪一路由策略层决定**
   （`electron/audio/strategies.ts`）：业务层只说 `application` / `system` / `none`，
   渲染层不再传「要不要声音」那种布尔值 —— 老界面那个 `withAudio: true` 会被翻译成
   `system`（**不是**普通 `loopback`）。原来的「带音频失败就退回 `audio: false`」那层
   降级重试已去掉：现在解析失败是**带着原因失败**（见下一条与 4.15）。
2. **`application` 模式真的能只采一个应用**（`applicationLoopback:<pid>`，实测别的那一路
   低 94~133 dB），所以「只听这一个游戏的声音」在**采集层**已经成立。
   但**界面上还没有入口** —— 这一版渲染层只给 `withAudio`、被翻译成 `system`，
   所以对用户还不能承诺，得等声音设置 UI 落地。它的边界（进程树只到
   直接子进程、窗口↔进程不是一对一）在 4.15。`system` 模式才是整机混音（减本实例），
   与选中的窗口/屏幕无关。
3. **不自动降级。** 请求 `application` 却拿不到目标进程时，唯一允许的结局是带原因失败，
   并附一个**可选**的 `suggestion: 'system'` 交给调用方决定 —— 绝不自己换成普通 loopback。
   那一路会把本机自己的播放（收到的远端语音）一起采进去，双向共享直接啸叫；
   悄悄换过去等于把「有声音」当成「做对了」。
4. **两端的约束必须一致。** 主进程的 handler 拿不到 `getDisplayMedia` 的约束，
   要由渲染进程通过 `capture:select-source` 把「这次要哪一路声音」一起传过去。
   渲染请求了 audio 而主进程没给，Chromium 会让整个采集直接失败。

静音是一处纯本机状态（`App.tsx` 的 `mutedPeers`），只切 `<video>` 的 `muted`，
**不发任何信令**：静音是「我不听」，不是「你不许说」，不该影响对端、也不该影响别人。
同理，本地预览那一路**恒定静音** —— 本机同时播放自己的系统声音会变成双份回声。

刻意不用 `loopbackWithMute`：那个会把本机自己的播放一并静音，而共享游戏的人自己要听声音。
`system` 模式用的是 `loopbackWithoutChrome` —— **排除本实例**的播放（实测压掉 22~58 dB，**run 之间会飘**），
但**别人的** Chromium 应用不受影响（共享浏览器窗口时不会被静音）。
这是为了断掉「采到自己发出去的远端语音 → 啸叫」，见 4.15。

### 4.11 双击放大规则

四路挤在网格里时需要能放大某一路。规则定死为五条：

| 动作 | 结果 |
| --- | --- |
| 双击任意**远端**画面 | 进入单路主画面，其余几路收进底部缩略条 |
| 点画面右上角的「放大」按钮 | 同上 |
| 再双击主画面、或按 `Esc`、或点「还原」 | 回到网格 |
| 单击缩略条里的任意一路 | 切换到那一路（不是"还原"） |
| 被放大的那个人离开房间 | 自动退回网格，不留空主画面 |
| 双击 / 放大**本地预览** | 无效果 —— 看自己没有意义 |

**鼠标入口不能只留双击。** Windows 上点击一个**非活动窗口**时，第一下会被
系统拿去激活窗口、不产生 `click`，于是「双击」实际要吃三下才成立 ——
用户看到的就是「点了完全没反应」。同一台机器上开两个客户端来回切时必然踩到，
而且只在第二个窗口上出现，看起来像 bug（2026-09-17 实测）。所以：
网格里给一个常驻的「放大」按钮（即使第一下被吃掉，第二下也一定生效），
底部缩略条那几格本来就小、用**单击**更顺手。

同时只允许放大一路。放大必然联动画质，这是四人场景不卡的前提：

```
放大某路  → 向该发送方请求 FOCUS(1080p30)
其余几路  → 请求 THUMBNAIL(360p30)
还原      → 全部请求 GRID(540p30)
```

为什么要顺手把其余几路降档：源端对每个观看者独立编码，四路 540p 已经吃掉大半上行，
不降档的话放大这一路也拿不到 1080p（带宽账见 4.2）。

实现落在 `App.tsx` 的 `focusedPeerId` + 一个 effect，画质复用的是既有的
`quality-request` 通路，没有新增任何信令。

### 4.12 窗口能被枚举，前提是它没被最小化

`desktopCapturer.getSources` 在 Windows 上会**静默跳过**下面这些窗口，
返回的列表里连一项都不给：

| 状态 | 判据（Win32） |
| --- | --- |
| 已最小化 | `IsIconic(hwnd)` |
| 不可见 | `!IsWindowVisible(hwnd)` |
| 标题为空 | `GetWindowTextLength(hwnd) == 0` |
| 被 DWM cloaked | `DwmGetWindowAttribute(hwnd, DWMWA_CLOAKED)` ≠ 0 |

**症状是「明明开着却说找不到」，用户拿不到任何线索。** 2026-09-17 实测（以撒的结合）：

```
hwnd=6163160  isaac-ng.exe  已最小化   ← 列表里没有它
同一 hwnd 回到前台时                    ← window:6163160:0 正常出现
```

**这解释了一类会被误当成「抓取不稳定」的现象**：全屏游戏切到后台时，
Windows 会自动把它最小化，所以「有时候能抓、有时候抓不到」——
实际由窗口是否最小化决定，不是随机。当时的描述是「只是被盖住，没最小化」，
实测状态是 `IsIconic = True`。

两条推论：

1. **最小化的窗口即使能枚举也抓不到画面**（DWM 不再为它出新帧），
   所以这不是「把列表补全」能解决的问题，只能让用户把窗口切回前台。
2. 产品上必须把这条写进界面（源列表下方的常驻提示），
   否则用户会一直以为是软件坏了。

**判据是「有没有最小化」，不是「是不是全屏」** —— 这一点别弄反：

- **被别的窗口盖住**：不影响。WGC 抓的是窗口自身内容，不是屏幕像素。
- **无边框全屏 / 窗口化全屏**：不影响。**2026-09-17 实测以撒在全屏状态下
  能正常抓到画面**，先前「全屏就抓不到」的说法是过度概括。
- **切到后台会不会被系统最小化，取决于游戏的显示模式**：独占全屏切出去
  通常会被自动最小化（于是下一轮枚举就找不到它了），无边框全屏不会。
  以撒实测属于后者，所以它「全屏也能抓」。
- 因此建议无边框窗口化的理由要从「否则抓不到」改成
  「切出去不会莫名被最小化，而且任何置顶窗口都能盖上去」，见 4.1。

另外，`setDisplayMediaRequestHandler` 里**不要**用「找不到就退到列表第一个源」兜底：
那会变成「选了 A 却共享了整个屏幕」，画面上看着像成功了、实际共享错了东西，
比直接失败难排查得多。找不到就失败，并把原因经 `capture:take-failure` 交给渲染层。

诊断工具：`scripts/probe-windows.py`（枚举全部顶层窗口并标出会被跳过的那些）、
`诊断窗口抓取.bat`（对照实验 / 持续监控两种模式）。

### 4.13 浮窗模式（全屏游戏时的观战窗）

目标：全屏玩游戏时把客户端缩成一小块压在游戏上面，只留画面。
「置顶」只是它的一部分，另外几件事不做，这个功能等于不存在：

1. **必须先放开窗口最小尺寸。** 常规模式写着 `minWidth: 1024, minHeight: 640`
   （`main.ts` 创建窗口时定的）。**不临时放宽，窗口根本压不下去** ——
   表现是「拖到某个大小就拖不动了」，不报错，很容易被误判成 CSS 问题。
   退出浮窗要还回常规档，而且**顺序两边都不能反**：进浮窗先放宽下限再 `setBounds`，
   退出先把下限还回常规档再 `setBounds`，否则尺寸会被旧下限卡住。
2. **进出时换一套窗口几何。** 进浮窗记住当前 `bounds`，退出原样还回去；
   否则用户用完浮窗，主窗口就永远停在那个小尺寸上了。
   最大化的窗口要先 `unmaximize()`，否则 `setBounds()` 无效。
3. **透明度只能走 `win.setOpacity()`，不能用 `transparent: true`。**
   后者在 Windows 上会跟「自由缩放」打架（透明窗口的 resize 有已知问题），
   而自由缩放是这个功能的硬需求。**代价是画面本身也会一起变淡**，这是明说的取舍。
   保留原生标题栏是同一个理由 —— 拖窗口和拖边框改大小都靠它，不用自己做 drag region。
4. **画面布局必须自己算。** 常规网格每格写死最小 280x160（`.grid`），
   窗口一缩小格子不跟着缩、会撑破容器。浮窗用 `pickFloatGrid()` 按容器实际像素
   挑行列数（判据是每格宽高比离 16:9 的**对数**距离，绝对差会把「偏宽」和「偏高」
   判成不同远近），行列数由 JS 算好 inline 写进 style。尺寸靠 `ResizeObserver` 拿，
   所以观察器**只在浮窗模式挂**。

其余规则：

- **浮窗只摆正在共享的那几路。** 浮窗的卖点是小，没在共享的格子空占一块地方没有意义。
  （常规模式照旧显示全部成员，那里要看的是「谁在线」。）
- **双击放大在浮窗里仍然有效，且只重排窗口内部比例，不改窗口尺寸。**
  放大态 = 主画面吃满 + 底边缩略条；缩略条另用一套尺寸（96x54），
  常规模式那个 168x95 会占掉浮窗一大半高度。
- **格子上的标签和底部统计在浮窗里默认隐形，鼠标移到那一格才出。**
  玩游戏时鼠标在游戏里，正常情况下浮窗上不该挂着一排字挡画面。
- **控件（透明度滑杆 + 退出浮窗）是 hover 才浮出来的悬浮条** ——
  浮窗里没有侧栏可以放它们。退出另有全局快捷键一条路。
- 「浮窗模式」是全局快捷键 `Ctrl+Alt+G`。**必须全局而不是窗口级**：全屏游戏里
  鼠标在游戏里点不到界面，窗口级快捷键在窗口不聚焦时也收不到按键。
  代价是**多开客户端时只有一个实例抢得到**，抢不到的在界面上标「快捷键冲突」。
- 窗口尺寸 / 位置 / 透明度持久化在 `userData/float-window.json`（零依赖，用 node 的 fs）。
  **多开客户端时几个实例共用这一份** —— 浮窗尺寸本来就该是「这台机器上的小窗长什么样」，
  共用符合直觉，代价是几个实例会互相覆盖。
- 存下来的位置如果落在已经不存在的显示器上（外接屏拔了、分辨率变了），
  会退回默认位置（贴右下角）—— 总比记着一个看不见的坐标好。

**屏幕层级前提**：`setAlwaysOnTop(_, 'screen-saver')` 落到 `HWND_TOPMOST`。
`level` 参数在 **Windows 上同样有效**（文档标了 macOS / Windows）：`pop-up-menu`
及以上会显示在任务栏之上。三档「游戏全屏」的结论完全不同：

| 游戏的全屏方式 | 浮窗能不能压住 |
| --- | --- |
| 无边框窗口化 / 窗口化全屏 | **能**，最稳 |
| 「全屏」但走全屏优化（FSO）→ 实际是 DWM 合成 | **能** |
| 独占全屏（DXGI FSE，或在 exe 上勾了「禁用全屏优化」） | **不能**。DWM 让出合成权，任何普通窗口都盖不住 |

判定某款游戏属于哪种：看它全屏时能不能被采集到 —— 能采到就是合成的（见 4.12）。
**独占全屏那档只能让用户在游戏设置里改成无边框窗口化**，我们没有别的办法。

> Steam / Discord 的 overlay 能显示在独占全屏上，靠的是往游戏进程里注入 DLL ——
> 我们不做注入：那是另一个量级的工程，而且正好撞上 4.1 的反作弊风险。

**为什么还要一个 topmost 保活 —— 而且必须是 300ms 级**：Windows 上 topmost 是一个**带**，
带内谁在上面取决于谁最后一次 `SetWindowPos`，而**激活会把自己抬到带内最上面**。
关键在于：**不少游戏全屏时自己也置顶**，于是「用户点回游戏那一下」就会把浮窗压到带内下方
—— 这正是 2026-09-17 用户实测的「点回游戏，浮窗掉到低层」。所以浮窗模式下每 300ms
重断言一次（`setAlwaysOnTop(true, 'screen-saver')`）。

四种「抬回来」的招实测只有三种有效，保活用的是其中最简单的一种：

| 招 | 能不能抬回带顶 | 会不会抢走游戏焦点 |
| --- | --- | --- |
| `setAlwaysOnTop(true, 'screen-saver')` 重断言 | **能** | 不会 |
| `moveTop()` | **能** | 不会 |
| 先 `setAlwaysOnTop(false)` 再 `(true, 'screen-saver')` | **能** | 不会 |
| `showInactive()` | **不能**（它只管显隐，不碰 z-order） | 不会 |

**绝不能抢走游戏的焦点。** 用户对症状的原话是「调出浮窗之后游戏不能操控了」——
在 Windows 上这几乎总是焦点问题：游戏一旦不是前台窗口就收不到键鼠，
多数单机还会弹暂停菜单。实测**可聚焦时一次 `focus()` 就足以把焦点从游戏里夺走**，
所以浮窗模式下把窗口设成 `setFocusable(false)`（即 `WS_EX_NOACTIVATE`，
一个「点它也不会被激活」的窗口），之后连主动 `focus()` 都抢不动。
**退出浮窗时必须恢复 `setFocusable(true)`** —— 否则常规界面再也拿不到焦点，
那比不置顶严重得多。连带影响：不可激活的窗口通常也不再出现在任务栏 / Alt+Tab 里。

> 残留的诚实边界：**点我们自己的界面（顶栏开关、透明度滑杆）依然会把焦点从游戏拿走**，
> 这是「点了一个普通窗口」的必然结果，改不了。所以进浮窗优先用全局快捷键 ——
> 键盘那一下不碰焦点。

**已验（`npm run check:topmost`，2026-09-17 起 22 项全绿）**：开一个无边框全屏窗口模拟
「游戏」，再用 `desktopCapturer` 截屏读像素判定谁在上面（窗口层级没有可读的 API）。
**每组都带对照** —— 因为「测法本身有没有效」比结论更重要：

```
对照组（浮窗未置顶）        ✓ 浮窗被全屏窗口盖住      ← 这条在证明测法本身有效
置顶组                     ✓ 浮窗压在全屏窗口之上
抗抢组（游戏不置顶，抢最前） ✓ 浮窗仍压在上面          ← 「真置顶」的判据
最小化 / showInactive       ✓ 能还原，且还原后置顶还在
同带竞争组（游戏也置顶）     ✓ 游戏夺回带顶            ← 复现真实场景，量出保活该多快
抬回来组（四种招）          ✓ 三种有效、showInactive 无效；四种都不抢焦点
保活时延组                 ✓ 直接读源码常量断言 ≤400ms（已反向验证会红）
焦点保护组                 ✓ 先证明 focus() 抢得走，再证明不可聚焦时抢不动
```

⚠️ 它验的是**「无边框全屏窗口」**这一档；**独占全屏模拟不出来**，只能拿真游戏实机试。
也**验不了真实游戏自己的脾气**（它可能自置顶、可能一被遮挡就暂停或退出全屏）。

**范围决策（2026-09-17 需求方拍板）：接受现状，不再往独占全屏走。**
突破独占全屏只有「注入游戏进程」一条路（Steam / Discord overlay 的做法），
代价是另一个量级的工程，而且正好撞上 4.1 的反作弊风险 —— 需求方判断不值。
**玩法统一到「无边框窗口化」**（实机跑下来浮窗在该模式下正常），
它就是浮窗功能的验收口径。**M6 剩下那半（独立叠加层 / 鼠标穿透 / 编辑锁定双模式）同样不做** ——
那些是为「压在独占全屏上」服务的，前提没了，跟着一起停。

> 一条关于测量本身的记录：**单次像素抽检要 0.2~0.9 秒**（实测有一轮到 945ms），
> 比 300ms 和 1500ms 的差别还粗。所以「保活够不够快」不能靠恢复时间判定 ——
> 判据是**读源码里的 `TOPMOST_KEEPALIVE_MS` 并断言 ≤ 400ms**；恢复时间那条只用来
> 证明「保活真的在抬，不是代码根本没跑」。

**快捷键的两种语义**（`toggleFloat`）：浮窗模式下窗口被最小化时，`Ctrl+Alt+G`
的意思是「把浮窗叫回来」，不是「退出浮窗模式」—— 否则用户按了没反应，只会以为软件坏了
（`setFloatEnabled` 开头那句 `next === enabled` 会直接早退，所以必须在这之前拦）。
唤回**只能用 `showInactive()`**，不能换 `restore()`：后者会激活窗口，把焦点从游戏抢走，
等于一按快捷键游戏就失焦。进入浮窗时若窗口是最小化的，同样先 `showInactive()` ——
对最小化的窗口 `setBounds()` 是不生效的。

**无边框窗口（2026-09-17 第八批）**

主窗口是 `frame: false` 的。理由不是外观，而是**不可激活的窗口没有可用的非客户区**：
浮窗模式下窗口刻意 `setFocusable(false)`（见上），而**原生标题栏拖动、边框缩放，
以及最小化 / 最大化 / 关闭这三颗系统按钮，全都要求先激活窗口** —— 在不可激活的窗口上
它们一个都不响应，而且**不报错**。2026-09-17 两轮实机反馈说的都是这块死角
（先「浮窗拖不动」→ 补了自绘拖动；再「那三颗按钮也无效」），最后靠**整个去掉原生边框**收口。
**只修拖动、留着边框等于没修** —— 用户照样只看到一条按下去没反应的边。

去掉之后整窗都是页面，两件事自己补：

| 场景 | 谁负责 | 判据 / 怎么验 |
| --- | --- | --- |
| 常规模式拖动 | 顶栏整条 `-webkit-app-region: drag`（子控件必须 `no-drag`） | 按下点**被浏览器吞掉**（页面收不到 `pointerdown`）＝ 命中生效；`scripts/_probe-app-region.cjs` |
| 常规模式三颗按钮 | 自绘 `.app__winctl` → `win:minimize` / `win:toggle-maximize` / `win:close` | `check:tiles` 第 5 组 5 条（真 preload → 真 IPC） |
| 浮窗 / 拆分模式拖动、缩放 | 自绘 `float-drag.ts` → `float:move-to` / `float:resize-to` | `check:tiles` 第 4/5 组 + 真鼠标探针 |

**最大化状态必须由主进程推回页面**（`win:maximized`）：**双击拖动区也会最大化** —— 那是系统行为、
不经过我们的按钮，渲染层自己记的话图标立刻说反话。

**三档最小尺寸不能打架**：浮窗 260x150 → 折叠控制条 620x76 → 收起后那颗小球 152x40，
三轮的是**同一扇窗口**。每一轮都必须**先 `setMinimumSize(这一档的宽, 这一档的高)` 再 `setBounds`**，
否则新尺寸会被上一档**静默夹回**：控制条的 76 被浮窗下限夹回 150（窗口高一倍、
控件下面空一大块）；小球更狠 —— 152 被 620 夹、40 被 76 夹，**两个方向一起错**。
`restoreHost` 要把下限还回 260x150，否则合并回来的浮窗再也缩不小。
夹的动作不报错、也没有任何 API 会回一句「你要的尺寸被抬了」，只能主动问 `getBounds()`
——`check:tiles` 第 5 / 7 组就是干这个的（判据写成「实际值 == 按常量算出的期望值」，
常量从源码里读，顺带钉一条「读到了吗」防正则失效）。

顺带一条：`barCollapsed` 是**拆分模式里的东西**，`restoreHost` 要一并清掉它，
否则下次进拆分时窗口会直接以小球的尺寸出现。

**代价（写在明处）**：顶栏整条是拖动区 ⇒ **顶边不能再拉着改高度**（左右下三条边照旧）；
窗口失去原生描边，自己补了一圈 `outline`；`win:*` 这几个 channel 的**名字在 preload
与主进程各写一份**（分属两个 tsconfig、类型也共享不了），对不上就是「点了没反应」——
所以 `check:tiles` 里专门有一条对账。

⚠️ **`-webkit-app-region` 那条拖动本机自动化验不了**：合成鼠标（`SetCursorPos` + `mouse_event`）
驱动不了 Windows 的模态移动循环，只验得到「拖动区命中生效」这一半
（`scripts/_probe-app-region.cjs`：拖动区 `pointerdown=0`、普通区域正常收到）。真鼠标手感只能实机试。

#### 4.13.1 拆分模式：每路画面一个独立小窗（2026-09-17）

浮窗默认把正在共享的几路摆在**一个**窗口里。拆分模式把它们拆成**每人一个独立小窗**，
各自能拖到屏幕任意位置、各自缩放。**窗数 = 总人数 − 1**（4 人房 → 3 个小窗）。
它是**浮窗的子模式**：退出浮窗必须连带把小窗全部收掉（`closeAllTiles`），否则会留下一地孤儿窗。

**① 为什么必须「搬像素」而不是搬轨道。** 最省事的做法是把 `MediaStreamTrack` 直接交给小窗
（零解码、零画质损失）。**不行** —— 实测（`scripts/_probe-track-xfer.cjs`，两个窗口、8 秒）：

```
✗ DataCloneError: Failed to execute 'postMessage' on 'MessagePort':
  Value at index 0 does not have a transferable type.
✓ clone 出来的两条轨道都是 live        ← clone 本身没问题，是「过不了进程边界」
✗ 小窗 5 秒 0 帧 / 采样全 null
✓ 主窗口那一路 5 秒 150 帧（≈30fps）   ← 反过来把原件让给小窗也不行，主窗口会瞎
```

所以只能由**主窗口当帧源**：主窗的 `<video>` 解码 → `drawImage` 到一张 canvas
（缩到该小窗的目标尺寸）→ `createImageBitmap` → 经 `MessagePort` 转移。
三个硬约束：

| 约束 | 不这么做的症状 |
| --- | --- |
| `ImageBitmap` **只能走 `MessagePort` 的 transfer list**（第二参数），**走 IPC 结构化克隆传不过去** | 小窗永远收不到帧 |
| 驱动用 **`requestVideoFrameCallback`**，**不是 `requestAnimationFrame`** | 源 30fps 会被按刷新率搬两遍（搬的是同一帧），fps 数字假高、白烧 CPU |
| 每路**各用一张 canvas**、且**同时只允许一帧在途** | 共用画布会互相覆盖成别人的帧；不限流会把渲染进程堆爆 |

**② 成本**（`scripts/_probe-frame-pipe.cjs`：3 路 720p@30fps 源 → 3 个小窗 360x203）：

```
源出帧      : [30.2, 29.8, 29.6] fps     ← 驱动没跑偏：按源节奏，不是刷新率
小窗显示    : [30.4, 29.8, 29.8] fps     ← 跟得上源
延迟(均/峰) : 3/5ms | 3/5ms | 3/5ms       ← 主窗画完 → 小窗画出来
CPU 平均    : 主窗口渲染进程 3.3% · GPU 3.4%   （基线：只跑源不搬帧 = 0.7% / 2.0%）
              每个消费小窗的渲染进程各自 0.3%
1 路拖大到 720x405：延迟 2/2ms，主窗渲染进程 1.2%
```

读法：**搬帧的净开销 ≈ 每路 0.9 个点 CPU / 0.5 个点 GPU，延迟 3ms 量级**，
对 30fps 观战完全够用。代价是**每个小窗一个独立渲染进程**（三窗 ≈ +0.9% CPU 外加三份
渲染进程内存）—— 这是「真原生窗口、各自拖放」必须付的钱。

**③ 声音不出现在小窗里，留在主窗口。** 小窗只画图、不放 `<audio>`：loopback 是**整机混音**
（见 4.10），一路一条音轨本来就没法按小窗拆开；声音留在主窗口那条窄控制条里，
静音逻辑不用复制一份，也不用跨进程同步播放状态。

**④ 主窗口收成控制条时，画面层必须留在 DOM 里继续跑。** 控制条是 620x76（`BAR_WIDTH/HEIGHT`），
画面那层视觉上必须收掉，但**不能让它退出布局** —— 用 `opacity: 0`：

```css
.hostbar__videos { position: absolute; inset: 0; opacity: 0; pointer-events: none }
```

> **诚实边界（2026-09-17 复跑探针后更正）**：`scripts/_probe-hidden-video.cjs` 用合成源
> （`canvas.captureStream`）测六种藏法，**六种拿到完全一样的 151 帧 / 5 秒**（完全可见 /
> 2x2 像素 / `opacity:0.01` / 被容器裁到 2px / `visibility:hidden` / `display:none`），
> 两次复跑一致。**也就是说「`display:none` 会停止出帧」这句话没有被复现出来** ——
> 它是实现当时的保守假设，不是实测结论。真实解码源（远端 WebRTC 轨道）没验过，
> 而 `opacity:0` 在任何情况下都成立，所以**规则不变，但理由要改成「保守选择」**：
> 别去换 `display:none`，不是因为它一定坏，而是因为换了没有收益、只有风险。

**⑤ 换人不重建窗口。** 同一位置换了个人（对方离开、别人补进来）**不重新创建 / 导航小窗**
（会闪一下白屏），只把新身份**从通道上推过去**（`connectTile` 的 `meta` 带
`{ index, peerId, name }`，见 `TilePortMessage`）。**身份必须跟着通道走，不能只留在 URL 里** ——
页面不重新导航，URL 永远不变，于是小窗会一直挂着上一个人的名字、静音按钮也会对着错的通道说话。
同理 `muted` 必须随 `syncPeers` 透传，否则小窗按钮显示的状态和实际相反。

**⑥ `contextIsolation: false` 是这条链路的前提 —— 主窗口也不例外（2026-09-17 更正）。**

`MessagePort` 过不了 `contextBridge`（它只搬可序列化的值）。隔离打开时交到页面手里的
**不是端口，而是一个没有任何方法的普通对象**，而且**不报错**。实测
（`scripts/_probe-bridge-port.cjs`，带对照组）：

```
① 过桥（contextIsolation: true）   ：port=[object Object] · postMessage 不是函数 · 主进程收不到回信
② 不过桥（contextIsolation: false）：port=[object MessagePort] · 一来一回正常
```

**实测踩到过这一条**：主窗口当初是 `contextIsolation: true`，于是「拆成 3 个小窗」之后
三个小窗全黑、一直停在「等待画面…」，**控制台一个字都没有**。成因是双重静默 ——
空对象是真值（`if (!port)` 这种判空照样过），于是帧泵照常启动，之后每一帧都在
`postMessage` 上抛 TypeError、又被帧泵自己的 `.catch` 吃掉。
现在装了三道闸：主窗口 `contextIsolation: false`；帧泵显式认
`typeof port.postMessage !== 'function'` 并写进日志；验收脚本改成断言
**「主窗口发一张位图过去、看小窗收没收到」**（原先只断言「小窗收到了通道」——
那条当时**是绿的**，因为坏的是主窗口那一端）。

代价可控：两个窗口加载的都是我们自己的本地页面、`nodeIntegration` 仍为 false，
preload 也只是把 IPC 包一层。**哪天要在主窗口里渲染外部内容（聊天、网页预览之类），
这一条必须重新评估。**

**⑦ 浮窗的拖动与缩放必须自绘。** 浮窗是 `setFocusable(false)` 的窗口（理由见上一节第 5 条），
而**系统的标题栏拖动与边框缩放都会先把窗口激活** —— 在非激活窗口上这两条路都不成立。
用户看到的是「浮窗拖不动、也拉不大」，而且**没有任何 API 会把这个错误报出来**，
只能靠实机发现（同样是他 2026-09-17 测出来的）。做法与小窗一致：渲染层自己算屏幕坐标，
走 IPC 让主进程 `setBounds`（`float:move-to` / `float:resize-to`，**只在浮窗模式下受理、
且只认主窗口** —— 小窗手里也握着 `ipcRenderer`）。拖动区就是整块画面区，
缩放走右下角自绘手柄（自绘控件没人试就等于不存在，所以要画出来）。

判据（`check:tiles` 第 4 组）：在「进浮窗后窗口确实不可聚焦」的前提下
`moveTo` / `resizeTo` 真的改得动几何；`resizeTo(10,10)` 被下限抬回 260x150
（拖成一条虚线的**置顶**窗口就再也点不到了）；**别的窗口发来的请求被丢掉**（对照组）。

**⑧ 小窗上的常驻元素必须让开指针。** 拆成多个小窗之后，几个小窗长得一模一样，而名字原先
挂在**鼠标进小窗才会浮出来**的那条底部悬浮条里 —— 想分清哪个是谁，得把鼠标逐个划过去，
实用上等于没有。改成贴左上角的**常驻名字牌**（13px，原来那条是 11px）。
常驻的代价是压住一小块画面，所以三条都得守：半透明深底 + 文字阴影（底下是随时在变的
游戏画面，纯文字读不出来）；**`pointer-events: none`**（小窗整面都是拖动区，名字牌要是
接住那一下，正好从它上面开始拖就拖不动了 —— 症状是「只有左上那一小块拖不动」，很难归因）；
**不用 `backdrop-filter`**（小窗画面是每帧重绘的 canvas，背景模糊等于每帧多一次全窗重采样，
为一行字不值）。静音状态也借它一并常驻：画面在动却没声音时，人会先去怀疑画面，
不会去怀疑那个开关。

**⑨ 控制条能像悬浮球一样收起来（2026-09-18）。** 拆分之后那条 620x76 的控制条常驻贴屏幕底部，
挡视线又没处躲，所以给它一个「收起」：点一下，**主窗口直接缩成屏幕右下角一颗 152x40 的胶囊**
（`setBarCollapsed` → `float:set-bar-collapsed`），再点一下就展开。三条是这个交互的全部：

- **球上不能有按钮。** 整块是拖动区（收起态 `.app__stage` 挂的是 `floatBallProps`），
  按钮吃掉哪一块，哪一块就变成「从这儿开始拖不动」—— 和小窗名字牌同一个坑。
  所以展开靠**按位移判点击**：按住后位移 ≤3px（`TAP_SLOP`）算点了一下、否则算拖动；
  `pointercancel`（拖到别的显示器被系统中断之类）**一律不算点击**，不然一次中断
  就会把球自己展开。
- **控件和画面要分开收。** 收的只是控件（球上写着「N 个小窗」），**那层搬帧用的画面必须留着**
  —— 它是帧泵的源，跟控件一起收掉就是所有小窗全黑、且不报错。判据不看「它在不在」，
  而是「它归不归 `barCollapsed ? … : …` 那个三元管」：静态断言先框出整个三元，
  再要求这段里没有它、且它前面那截也不许出现 `barCollapsed`。
- **界面等主进程推回来再切。** 尺寸是主进程改的，渲染层自己先切会出现一帧
  「球画在一条 620x76 的窗口里」；`invoke` 的返回值里就带着 `barCollapsed`，
  直接落状态即可，`float:tiles-status` 那份推送是幂等冗余（但断言里要单独钉它一次，
  「状态到了」≠「界面切了」）。

> **一条没留下的断言（2026-09-18）**：原先还量了「源窗口压到 152x40 后仍在出帧」，
> 反向验证时它**红不了** —— 把源页那三个 `<video>` 改成 `display:none`（比缩小彻底得多），
> 帧率照样是满的：`requestVideoFrameCallback` 不看元素可见性（同 ④ 那条「保守选择」的结论）。
> 抓不到东西的断言就是假保障，删掉，换成上面那条静态的（它抓的才是真实失效模式）。

**取证**：4 条静态断言（`check:tiles` 静态组）钉住「不在 hover 条里 / 常驻且有定位 /
不吃指针事件 / 静音跟着变色」，外加 `scripts/_probe-tile-name.cjs` 的**真页面截图像素对照**：
把名字牌 `display:none` 掉再截一张，名字牌那块平均亮度 **53.2 → 0.0**，而画面别处
**0.0 → 0.0**（证明它真的占了像素、且只占左上角一小块）；同时动态验一次
「名字牌上按下仍落在拖动区里」。占画面比例实测：320x200 小窗 + 11 字长名字占 **6.7%**，
真实名字（2~6 字）约 2~3%。

**⑩ 浮窗的控件入口必须常驻可见（2026-09-18）。** 实测只开自己一端就切进浮窗，
屏幕上只有一句「进入房间后，这里显示其他玩家的画面」和一块共享画面 —— **一个控件都没有**，
想退出去只能靠 `Ctrl+Alt+G`。两个原因叠在一起，缺一条都不会长成这样：

- **分支顺序**：控件原先挂在 `.app__stage` 里 `isFloat ?` 那个分支内，而分支链最前面
  还有一层 `!inRoom`（就是那句提示）—— 没进房时整块被它接走，**控件连渲染都没有**。
  所以控件现在排在**分支链之外**（`isFloat && !splitActive`），空态照样渲染。
- **靠 hover 浮出**：进了房之后那条也一样是 `opacity: 0`、等鼠标进窗才浮出来 —— 而浮窗
  恰恰是「鼠标在游戏里」的场景，用户根本不知道有它。**「只在 hover 时才出现」等于没有**
  （与小窗名字牌同一条判据，见 ⑧）。

做法：左上角一个**常驻的半透明小方块**（`.floatmenu`，53x22，`opacity 0.55`、鼠标上去变实）
当唯一入口，点一下展开那条控件、再点一下收回。那条**不再跟 hover 走** —— hover 出来的
东西收不掉：刚点完「收起」而鼠标还在窗口里，它下一秒又浮回来，看着像按钮坏了。
两处细节不能省：`max-width: calc(100% - 72px)` + `flex-wrap`（不设的话窄窗里这条横向溢出，
被挤出窗口的是左端的把手与滑杆；它还可能与入口小方块叠在一起 —— 而条上没有第二个收起入口，
入口被压住就再也收不回来）；右下角的缩放手柄跟着改成**常驻半透明**（同一条理由：
自绘控件没人试过就等于不存在）。

**取证**：`check:tiles` 第 8 组 —— **真页面**（`vite build` 的产物 + 真 preload）、
**没进房、不 hover** 地量：入口可见且 `opacity ≥ 0.3`、那条是收着的、**像素对照**
（把入口 `display:none` 掉，入口那块平均亮度 **36.5 → 16.9**，画面别处 **23.1 → 23.1**）、
**真鼠标 `sendInputEvent`** 点一下展开 / 再点一下收回、宽窗与最窄窗（260x150）下**整条**
都完整落在窗口里、以及展开的条与入口矩形**不相交**。静态断言接不住前两条：
元素被 `!inRoom` 拦掉时，源码里那几个字符串照样在。

**取证**：`npm run check:tiles`（**117 项，八组**）——
① **装载组**跑真模块 + 真 IPC（窗数 / 各标志位 / 控制条几何 / 换人不重建且拿到新身份 /
静音双向 / 用户手关后状态跟着变 / 合并还原 / `closeAllTiles` 不留孤儿 /
**主窗口那侧端口真的可用、发过去的位图真的到得了小窗**）；
② **帧泵组**（3 路合成源 → 3 条 `MessageChannelMain` → 3 个消费画布，
按颜色断言**不串台**、≥24fps、送出去的位图 ≤ 360x203）；
③ **浮窗拖动组**（见 ⑦）；
④ **静态断言组**（几处「改错了就静默失效」的写法：主窗口隔离、preload 不走桥、
帧泵认得出坏端口、拖动只在浮窗受理且只认主窗口、缩放下限、球里不许有按钮、
最小尺寸与 bounds 的先后…）；
⑤ **拆分叠在浮窗上**（三档最小尺寸打架那条路，见 4.13）；
⑥ **剪贴板组**（真 preload → 真 handler → 真系统剪贴板，见 4.14）；
⑦ **收起组**（控制条 → 右下角那颗球：三档里最容易被静默夹住的一档，真 preload → 真 IPC
量几何、断言 `barCollapsed` 跟着状态推回页面、小窗一个不少、幂等、没进拆分时不乱动，见 ⑨）；
⑧ **控件入口组**（真页面、没进房、不 hover，见 ⑩）。
⚠️ **鼠标真拖画面 / 拉手柄、悬停条这些纯 UI 交互仍然只有实机能验** ——
这组脚本盖的是「IPC 落不落得下去」，盖不了「拖起来手感对不对」。
（小球那套「按住能拖、松手没动过就算点一下」是自绘的 pointer 事件、不经过系统模态循环，
理论上合成鼠标驱得动；目前只有几何与静态断言盖着，没单独写这一条。）

### 4.14 剪贴板：复制房间码必须走主进程（2026-09-17）

**症状**：「复制」「复制邀请」两个按钮**按下去毫无反应**、不弹任何提示。
日志面板里其实躺着一行「复制失败，请手动记录房间码」—— 但日志默认折叠，用户看不到，
于是结论就是「这两个按钮是坏的」。

**病因是两层叠出来的**（`scripts/_probe-clipboard.cjs` 分四个场景量，缺一条就会开错药方）：

| 场景 | 实测结果 |
| --- | --- |
| 权限放行 + 窗口聚焦（`file://` 页面） | 写入成功，系统剪贴板 50ms 后读回一致 |
| 用 `main.ts` 原样的权限白名单 | `NotAllowedError: Write permission denied` |
| 权限放行 + `setFocusable(false)`（浮窗模式） | `NotAllowedError: Document is not focused` |
| 主进程 `clipboard.writeText` | 写读一致，不看权限、不看焦点 |

1. `main.ts` 的 `setPermissionRequestHandler` 只放行 `media` / `display-capture`，
   其余一律 `callback(false)`。剪贴板写入要的权限不在白名单里 ⇒ 渲染层直接抛
   `NotAllowedError`，而 `App.tsx` 把这个异常 catch 成了一行日志。
2. **光把白名单放开不够** —— 浮窗模式下窗口刻意 `setFocusable(false)`（见 4.13），
   而 Chromium 的异步剪贴板 API 要求文档处于聚焦状态，失败原因**从「没权限」变成
   「没焦点」，照样子失败**。浮窗恰恰是最想复制房间码发给朋友的场景。

**做法**：新增 `electron/clipboard.ts`，注册 `clipboard:write-text`；渲染层
`writeClipboard()` → `window.gameShare.clipboard.writeText()`。主进程的 `clipboard`
模块既不看权限也不看窗口焦点，常规模式与浮窗模式共用同一条路。权限白名单**保持不动**
（不要为了图省事把渲染层的剪贴板 API 放进来）。

**为什么单独成一个模块**：与 `window-mode.ts` / `float-tiles.ts` 一致（主进程的 IPC
注册各自成文件），同时让 `check:tiles` 能 `require` 到**编译产物**跑真链路 ——
handler 留在 `main.ts` 里的话，校验脚本只能自己抄一份，那等于自己给自己发合格证。

**复制成功要可见**：按钮短暂变成「已复制」（`.btn--done`）。剪贴板是看不见的东西，
复制成功却毫无动静时，用户没法判断成了没有 —— 只会以为按钮还是坏的（这条反馈里
「毫无反应」有一半是这么来的）。

**取证**：`npm run check:tiles` 第 6 组（真 preload → 真 handler → 真系统剪贴板）
- 断的是**主进程读回来的原文 == 渲染层发过去的原文**。只看 IPC 返回 `true` 是不够的：
  反向验证时正是这个形态 —— handler 照样返回 `true`，系统剪贴板里还是哨兵值
  （「通道到了」≠「数据到了」，同 4.13.1 的帧泵）；
- 空串被拒、且不覆盖剪贴板里原有内容（否则用户粘出来是空的，还以为复制坏了）；
- **对照组**：按 `main.ts` 的白名单姿态装一个权限处理器，断言渲染层那条路**写不进去**
  —— 这条用来证明上面那条 IPC 不是多余的（跑在 `file://` 页面上，与打包后主窗口一致，
  免得失败原因变成「不透明源」而不是那条权限）；
- 静态防回退：`main.ts` 真接上了 `registerClipboardHandlers`、preload 与主进程的通道名
  一致、渲染层没有 `await navigator.clipboard`、两个按钮都有「已复制」反馈。

### 4.15 音频采集：四种模式与 device id（2026-09-18）

`apps/desktop/electron/audio/` 这一层只干一件事：把「模式 + 目标」翻译成 Chromium 的
device id，拿不到就**带着原因失败**。采集本身仍然全由 Chromium 的音频服务承担。

#### 四种模式

| 模式 | device id | 采到什么 | 定位 |
| --- | --- | --- | --- |
| `application` | `applicationLoopback:<pid>` | 目标进程 + 它的**直接**子进程 | 正式，共享窗口时的默认 |
| `system` | `loopbackWithoutChrome` | 整机混音**减本实例** | 正式，共享屏幕 / 要全部声音 |
| `none` | —（不给音轨） | 无 | 正式 |
| `loopback` | `loopback` | 整机混音（含本实例自己） | **调试 / 高级兼容**，要 `GAMESHARE_ALLOW_RAW_LOOPBACK=1` |

- **device id 的唯一产地是 `electron/audio/device-ids.ts`。** Electron 会把这几个字符串
  当 Chromium 的 device id **原样透传、不做白名单校验**（Electron 的类型只声明了
  `loopback / loopbackWithMute / WebFrameMain`）⇒ 写错一个字符没有任何编译期提示，只有一句
  「采集失败」。所以别处不许再出现这些字面量，有静态断言盯着。
- **这四个 id 需要 Electron ≥ 43**（Chromium 130 上 `applicationLoopback:<pid>` 起不来）。
  这条只是**静态前置条件**，真正的判据永远是「采到了什么内容」。
- `parseHwndFromSourceId` 从 `window:1708206:0` 里取 HWND（中间那段就是句柄）；
  屏幕源 `screen:0:0` 没有 HWND。**解析不出来一律 null，不猜** —— 猜错的代价是
  「共享了另一个应用的声音」这种看着像成功、实际张冠李戴的失败。

#### 三条必须记住的边界（都是实测，不是推断）

1. **进程树只到「目标 + 直接子进程」，不含孙子。**
   反例值得留一个：拿目标应用 spawn 出来的**另一个 Electron 应用**去测，它的声音**采不到**
   —— 那个应用的音频出自它的**渲染进程**，对目标来说是孙子。能采到的，是**自己持有音频流**
   的直接子进程（实测用 Python + `winsound` 验的）。
   对产品：目标应用自己播的一定采得到；它启动的子进程里那些自己出声的（多数启动器 /
   音频助手）也采得到；再往下一层不行。
2. **窗口 ↔ 进程不是一对一**（Edge 一个进程挂多个窗口、UWP 由 `ApplicationFrameHost` 持有…）。
   所以只承诺「按应用」，**不承诺「按窗口」**。
3. **`applicationLoopback:<pid>` 的 id 在 `getSettings().deviceId` 里是加盐哈希**
   （`loopback` / `loopbackWithoutChrome` 原样返回）。采集链路无法从渲染层核对那个真字符串，
   所以验收只能靠**策略层纯函数断言** + 「同一个 pid 两次一致、不同 pid 两两不同」的观察。

#### 打包：koffi 必须留在 asar 外

HWND → PID 是**唯一**一处 FFI（`win32-window-pid.ts`：koffi 加载 user32 的 `IsWindow` /
`GetWindowThreadProcessId`）。**不写 WASAPI、不写 C++ AudioClient、不写自己的 PCM 管线。**

- `build-electron.mjs` 里 koffi 必须 **external** —— 原生模块打进 bundle 就是把 `.node`
  的加载路径写死（dev 与打包后是两条不同路径）；
- `package.json` 的 `build.extraResources` 把它放到 `resources/audio-ffi/node_modules/koffi`，
  并把 `@koromix/koffi-win32-x64` 放在**同一个 `node_modules` 下**：koffi 按
  `../../../@koromix/koffi-<platform>-<arch>` 找自己的二进制，**摊平摆放就会「文件都在、加载就炸」**；
- 拿不到 koffi 时**不静默降级**，直接抛 `ffi-unavailable`（带 `suggestion: 'system'`），
  由上层决定是退回整机声音还是把错误摆给用户。
- **漏了任何一条，症状都只是「按应用共享声音不可用」** —— 与「这台机器上就是没有 koffi」
  长得一模一样。所以 `check:app-audio` 直接去看**最新那份产物**的 `resources/`，
  并且真 `require` 进来、真调一次 `IsWindow`。这条是补出来的：第一次查产物时发现
  `release-4/win-unpacked/resources/` 下**根本没有 `audio-ffi`** —— 配置是后来补上的，
  补完从没真正打过一次包。

#### 取证

`npm run check:app-audio`（**67 项**）。判据全是「某个频率在 / 不在」而不是「API 没报错」——
音轨对象在设备静音、格式不对、采错进程时同样存在，看它等于没看。用六个互不相同的单频
（本实例 1060 / 目标 420 / 旁观 720 / 父 1360 / 直接子进程 1740 / 孙子 2040），
一次 FFT 就能把「隔离成立」和「整机混音」分得干干净净；频点是算出来的，
任何两个在场频率的谐波与和差产物都不落在别人的 ±25 Hz 带里。

四组隔离（Case 1 按应用 / Case 2 整机减自己 / Case 3 传父 pid / Case 4 传子 pid）
**都走真链路**：真 preload → 真 `capture:select-source` → 真 `setDisplayMediaRequestHandler`
（`capture.ts` 里那一份，不是抄件）→ 真 `getDisplayMedia` → 真 FFT。
另有一组专门盯着「必须失败」的输入（屏幕源要按应用、没开门禁就要 loopback、不认识的模式、
`none` 不给音轨），以及一组**对照组**：显式打开 `GAMESHARE_ALLOW_RAW_LOOPBACK=1` 之后
**必须听见自己的 1060 Hz** —— 否则前面那些「1060 无」可能只是这套 FFT 根本听不见 1060 Hz。

### 4.16 三轨媒体结构与数字反馈环（2026-09-18）

多人共享的媒体面是**三条 m-line**：`video` / `voice` / `appAudio`，顺序即
`packages/protocol/src/media-roles.ts` 里 `TRACK_ROLES` 的顺序，两端必须一致。
结构层只这几条规矩，但每一条都对应一类「看着像成功、实际不对」的失败。

#### 结构规矩

- **m-line 只由主动方创建**，方向恒 `sendrecv`；开关某条轨只用 `replaceTrack(null)`，
  **永不重新协商**。⇒ m-line 序号、mid、transceiver 与角色绑定一次就不再变。
- **角色识别只用 mid**（`roleForMid(t.mid)`）。`getAudioTracks()[0]` 这种下标在
  「关掉应用声音」「换源」之后就会张冠李戴。
- **voice 与 appAudio 必须是两条独立 m-line**，不共轨：接收端要分别静音；
  opus 策略相斥（语音要 DTX/低码率，音乐不能）；**AEC/NS/AGC 只属于麦克风** ——
  回环轨要是也开了这三件套，音乐和游戏音效会被当「回声」削掉。
- **停止共享 ≠ 挂电话**：`stopShare` 只摘 video + appAudio 两条轨，voice 照常。
- **换源必须先 `setLocalTrack(role, null)` 再 `capture.stop()`**，顺序反了旧应用
  的声音会继续从旧轨漏出来（stop 释放的是采集管线，轨还挂在 sender 上）。

#### 采集音频必须显式关掉三件套（本阶段最重要的实测）

`CaptureManager.#requestDisplay` 里 audio 约束必须显式写
`echoCancellation / noiseSuppression / autoGainControl: false`。
**不写就是真泄漏**：Chromium 默认给采集轨套 AEC，A 的扬声器里播着的 B/C/D 语音
被当作「回声」从回环轨里抑制 —— 实测 App Audio 里四路语音只比噪声源低 5~11 dB，
多人场景下就是数字反馈环半开。显式关闭后隔离度 **80~108 dB**（跨轮次稳定）。
这条与 4.15「别把三件套套到回环上」是同一件事的两个层面：那层说的是**产品语义**
（别削音乐），这层说的是**多人语义**（AEC 的参考信号会带进远端语音）。

#### `replaceTrack(null)` 之后 `track.muted` 不翻

不重协商意味着接收端那条轨**永远 muted === false**（m-line 还是 sendrecv），
判「对方把麦关了」**不能看 muted，只能量电平**：挂 AnalyserNode 建基线，
当前电平比峰值低 20 dB 即视为静默。验收页（`test/media-tracks.ts`）的生命周期
断言全部走这条口径。配套还有一个坑：**远端轨没出过流时 muted 本来就是 true**，
拿「muted 翻转」当退出条件会让观察循环第一轮就空转退出。

#### 验收

`npm run check:media-tracks`（`scripts/check-media-tracks.mjs` + `test/media-tracks.ts`），
两轮：

1. **structure**（合成源 + 假麦克风 `--use-file-for-fake-audio-capture`）：
   三轨 m-line 顺序/类型、mid→角色两端一致、各轨挂对、接收端分轨、
   生命周期（关麦→再开、关应用声音画面继续、换源旧轨真的 ended、停止共享不关麦）、
   交叉串线（两条音轨灌不同频率断言谁也没混进谁）。
2. **isolation**（真实回环，四人模型）：A 共享一个独立进程在出声的窗口
   （`application` 模式）+ 开麦，B/C/D 只开麦。判据是任务书正题：
   **A 的 App Audio 里不得出现四路语音 / Electron 提示音 / 远端媒体播放** ——
   满足这条，数字音频反馈链路才算真正解决。

两个仪器坑都写进过验收页注释：假麦克风的纯正弦量回来带 `主音 ± 250k Hz` 的旁带梳
（频点要落在梳齿缝里）；Windows 的窗口枚举是快照式的，刚就绪的窗口偶发漏一次
（`findNoiseSource` 带重试）。

### 4.17 产品化：音频三态、显式回退与分轨控制（2026-09-18）

阶段三的结构有了界面入口，这一节是**用户可见的行为契约**，改 UI 前先对它。

#### 共享声音三态（正式默认）

| 状态 | 底层 | 语义 |
| --- | --- | --- |
| **仅此应用**（默认） | `applicationLoopback:<pid>` | 所选窗口的应用及其子进程树 |
| 全部电脑 | `loopbackWithoutChrome` | 整机混音减本实例（远端语音不会被自己听回去） |
| 无声 | 无音轨 | 只发画面 |

窗口共享的正式默认是「仅此应用」；**屏幕源**没有所属进程，该选项对它不可用，
选屏幕源时显式落回「全部电脑」（选择器同步更新，用户看得见）。共享中切换模式
= 用同一个源按新模式重采（走换源流程，画面闪一下）——语义最干净，不做「热切换」。
另有「关闭/开启应用声音」按钮：只 `replaceTrack(null)` 暂停发送，不重采、不闪屏，
与模式选择是两个粒度的操作。

#### 显式回退，禁止静默降级

音频采集失败时**降级只到「无声 + 告警」**，永远不自动换普通 `loopback`（那会把
本机播的远端语音采回去，直接数字反馈环）。`state.audioFailure` 是**待用户决策**
的挂起项，UI 必须摆三个选项：改用全部电脑声音 / 继续共享（无声音）/ 取消共享。
换模式与停止走各自完整流程，「继续无声」才走 `acknowledgeAudioFailure()` 收起告警。

#### 换源时序：「先采新，成了再换轨」

`startShare` 对换源（含共享中改音频模式）的顺序是：新采集成功（`CaptureManager`
内部此时才停旧源）→ `setLocalTrack` 换新轨；**新采集失败时旧共享原封不动**，
错误交给 UI 提示「切换失败，已保留原共享」，绝不回滚成未共享、也不结束画面。
旧轨的 `ended` 与摘除由成功分支一次完成（见 4.16 的生命周期断言，回归门禁覆盖）。

#### 播放端：分轨音量与三态状态

- 每个远端两条角色轨各对应**一个** `<audio>` 元素（结构上保证同一 peer 不挂重复
  播放器），`volume` / `muted` 分轨独立：关共享声不影响语音，反之亦然。偏好只存
  本机（不发信令）；浮窗小窗空间有限，保留一键静音（作用两路）。
- tile 上显示**三个独立**状态徽标：语音（voice 轨在）、共享声（appAudio 轨在）、
  画面（sharing）。开麦但不共享声音、共享画面但无声音这类组合是合法状态，
  **不许把它们绑成一个总开关**。

#### Adapter 边界

业务层（`src/`）只见 `application / system / none / loopback` 四个模式名；
`applicationLoopback:<pid>` 等 Chromium 私有串**只存在于主进程
`electron/audio/`（Windows Audio Capture Adapter）**。未来 Electron 官方出稳定 API
时只换 adapter，业务层不动。

## 5. 客户端模块划分

规格文档提出的九个模块，逐一说明职责与依赖方向。**依赖只能自上向下**，
不允许下层反向依赖上层，避免 M6 的 Overlay 和 M4 的布局互相纠缠。

```
ShareSession       编排层：串起信令/采集/Mesh，对外暴露可订阅的不可变状态 ← apps/desktop/src/session
  │
SignalingClient    Socket.IO 封装、事件订阅、ack 请求、心跳
  │
CaptureManager     枚举窗口/屏幕、创建 MediaStream、切换源         ← M2（合成源已可用）
  │
MeshManager        成员列表 → 链路映射的同步（幂等增删、未就绪信令缓冲）  ← M1
  │
PeerLink           一条链路 = 一个远端 = 一个 RTCPeerConnection    ← M1
  │                协商 / ICE / 轨道挂载 / 画质参数 / getStats
QualityManager     档位策略（可替换：setParameters / simulcast）      ← M5
  │
LayoutManager      1/2/3/4 路布局、双击聚焦、Esc 返回                ← M4
  │
OverlayManager     独立 BrowserWindow、置顶、穿透、快捷键            ← M6
  │
SettingsManager    本地配置持久化
```

原规划的 `PeerManager` 落地时拆成了两个：`MeshManager` 只管「谁在房间里 →
该有哪几条链路」的同步，`PeerLink` 管单条链路的全部细节。

拆开的原因是这两件事的变化频率完全不同：成员增删是低频事件，
而单条链路的协商/重连/画质调整是高频状态机。
合在一起会让 M9 的重连逻辑和房间事件互相纠缠。

对应的，**信令转发必须容忍「链路还没建立就先收到信令」**：
对端可能先算出 offer 再发现自己还没为这个 peer 建链路。
`MeshManager` 用一个上限 256 条的缓冲队列接住这类信令，链路一建立就重放，
否则双方会互相等待对方先建链路，死锁。
`PeerLink` 内部对 ICE candidate 也有同样的缓冲（`#remoteDescriptionSet` 之前）。

### 客户端内置信令服务器（对规格文档的偏离）

规格文档把「信令服务」当成一个需要单独部署的东西。落地时改成
**客户端启动时顺手把服务器带起来**，理由是这个产品的使用者是几个约着一起看画面的人，
不是有运维的团队 —— 「先去命令行起一个 Node 服务」这一步足以劝退大多数场景。
默认开启，可以在侧栏「本机信令服务」面板里关掉。

实现上有三点要记住：

1. **`apps/signaling` 的库入口是 `embed.ts`，不是 `index.ts`。**
   `index.ts` 是进程入口，被 `import` 的一瞬间就会 `loadConfig()`、开始监听、
   注册 `SIGINT`/`SIGTERM`；当库引用会带着副作用跑起来。
   独立运行的能力完全保留（`npm run serve` 走 `index.ts`，打包产物仍是 `dist/index.js`）。
2. **`socket.io` 被打进 Electron 主进程**（主进程产物从 3.7KB 涨到约 700KB）。
   这不违反「desktop 的 dependencies 为空」：它走的是 devDependencies + 打包，
   和渲染进程打包 React 是同一套路子，electron-builder 仍然只需要搬 `dist/` 与 `dist-electron/`。
3. **端口被占用不算错误，是必须支持的正常状态。**
   本机已经有一个服务器时（用户自己起的，或同一台机器上开的第二个客户端），
   后启动的一方放弃监听、照常当客户端用，并在面板上说明原因。
   否则「本机开 2 个客户端互看」这条联调路径会直接不可用。

由此带来一条必须在使用说明里写清的边界：
**服务器的生命周期跟着客户端走。** 对端把客户端关掉，服务器就没了，
另一端会立刻断开 —— 这是设计如此，不是连接不稳定。

## 6. 连接策略与降级

```
iceTransportPolicy = 'all'（默认）
      host  ─►  srflx（STUN）  ─►  relay（TURN）
                                  ↑ 只有前三者全部失败才走到这里
```

判定当前走的是 P2P 还是 TURN：读 `getStats()` 里被选中的 candidate-pair，
看 `localCandidateType` / `remoteCandidateType` 是否为 `relay`。
M8 的验收方式是把 `iceTransportPolicy` 强制设为 `relay`，
确认视频仍能传输 —— 这能证明 TURN 链路本身是通的。

M8 之前 `buildIceServers()` 的 `turn` 参数传 `undefined`，
链路完全依赖 STUN + host candidate。
